# 沉浸封面分辨率与最小延伸规则

本文记录 2026-10-15 用户确认的规则，已在 iOS、macOS（Tauri）及全屏播放器消费接口中实现。历史文档中的 720×720、720×960 输出及生成前固定 1200px 解码限制属于此前实现，不是 Apple 推荐或要求的分辨率；普通 Now Playing 缩略预览仍可独立使用 1200px 的预算。

## 全屏播放器复用优先级（用户最新确认）

锁屏封面体验优先。全屏播放器是既有视频的消费者，不因播放器区域尺寸、显示缩放或方形外观要求重新编码一份视频。

1. 当前封面已有符合开关与播放策略的可用视频时，直接使用，不因像素尺寸较小或视频为 3:4 而拒绝复用；仍按 static → camera → depth 的既有优先级渐进替换。
2. 全屏播放器使用居中的 1:1 容器遮罩展示视频。3:4 视频可以在展示层裁切；遮罩不修改视频文件，不改变锁屏构图，也不使生成器为全屏额外延伸或另做方形版本。默认保持视频比例、填满容器，不拉伸画面。
3. 没有可用视频时，iOS 以锁屏需求为生成依据。锁屏的沉浸封面、沉浸动态封面展示开关只控制是否向系统发布对应 artwork，不作为视频生成或全屏读取的总开关；即使用户没有开启锁屏沉浸视频，全屏需求仍可触发生成并直接使用成品。全屏播放继续遵守暂停、Reduce Motion 和资源保护。
4. macOS 没有可用视频时，根据服务器原图制作最佳的 1:1 视频，不再按全屏区域像素需求设定生成上限。基础方形画布边长取原图长边，主体保持原尺寸、完整呈现，仅补齐短边方向；编码对齐、硬件编码能力与资源保护仍需处理，发生降级时应记录实际尺寸及原因。

这里的“直接使用”仍要求封面身份、模式和租约有效，不得使用其他专辑的视频。锁屏动画关闭不等于全屏动画关闭；系统要求减少动态效果或全屏自身需要暂停动画时，不因为缓存中存在动态视频而继续播放动画。

### 已确认的职责分离与流程

生成器负责准备视频；全屏播放器负责消费视频；锁屏发布器根据锁屏展示开关决定是否把视频交给系统。三者不能共用一个“锁屏未开启就全部禁用”的入口判断。

```text
全屏需要当前封面
  → 有可用视频：直接获取租约并显示，使用方形遮罩
  → 无可用视频：登记生成需求
      → iOS：按锁屏目标准备视频（尺寸来源及首次兜底见下节）
      → macOS：按原图准备最佳 1:1 视频
  → 静态 / camera / depth 各阶段完成后，全屏及时取用可用成品
  → 锁屏发布器独立检查展示开关
      → 开启：发布相应 artwork，复用成品
      → 关闭：不发布相应 artwork，全屏仍可使用成品
```

后续用户开启锁屏展示时，优先复用已生成且比例正确的视频；若新的系统请求要求不同尺寸，再按锁屏优先原则后台升级。前端取用接口与原生生产入口都需要检查，避免它们继续被旧的锁屏开关提前返回 `disabled`。

### iOS 请求尺寸的公开 API 边界

`supportedAnimatedArtworkKeys` 能主动查询支持的 1:1 / 3:4 格式，不能查询所需的具体像素尺寸。具体尺寸由系统调用 `previewImageRequestHandler` / `videoAssetFileURLRequestHandler` 时传入；Apple 不提供“现在主动询问锁屏需要几乘几视频”的公开接口，也不保证何时触发回调。预览和视频需求应分别记录，不能把某次预览尺寸冒充成系统的视频请求尺寸。

因此，“锁屏开关关闭也能生成”需要解耦生成需求与系统发布开关，不能靠临时开启锁屏展示或安装 animated artwork 来强行探测尺寸。

- 已获得相应格式的视频请求尺寸时，按该需求和原图分辨率生成，规则见下文；全屏直接消费同一资产。
- 尚无可用视频请求尺寸时，无法严格执行“先主动查询尺寸再生成”。实施建议是优先参考当前设备、当前格式最近有效的请求尺寸；完全没有记录时，以原图及原生屏幕像素范围确定临时目标，后续实际回调到来再后台升级。首次兜底的具体目标选取属于实现建议，不宣称为系统已经请求的尺寸。
- 尺寸记录需区分格式和请求类型，显示设备变化后重新评估，不能把某台 iPad 的一次请求变成所有设备的永久常量。

全屏可见状态通过独立的生成需求登记触发生产者工作；`acquire` 与视频 URL 回调继续仅读取成品，避免查询/轮询隐式启动重复推理。全屏关闭后释放需求和租约，锁屏自身的生成需求独立保留。

## 来源与输出上限

只有获取到完整、有效的服务器原始专辑图片后，才开始生成沉浸视频。继续以来源与完整性判断原图，不因为像素较小就认定服务器还存在更高分辨率版本，也不能使用已有缩略图抢先生成。

iOS 锁屏视频输出以系统请求的像素尺寸为上限，同时受原图有效分辨率约束：原图足够大时缩小到目标尺寸；原图不足时降低视频尺寸，不强行放大原图主体。输出不再统一固定为 720px，也不额外固定为 1080px 或 1536px。macOS 按上文的原图方形规则生成；全屏复用已经存在的视频时不再套用新的分辨率门槛。

Apple 的 [Providing animated artwork for media items](https://developer.apple.com/documentation/mediaplayer/providing-animated-artwork-for-media-items) 明确允许返回任意像素尺寸的视频，前提是与关联 artwork key 的宽高比相符。系统请求尺寸是本项目选择的输出上限，不应描述成 Apple 规定的统一编码分辨率。

锁屏输出读取相应视频请求中的像素需求。全屏播放器不再根据自身区域或屏幕缩放提出新的编码尺寸要求；也不能把所有 Apple 平台都固定为某台设备曾请求的尺寸。

## 最小延伸

生成时，在 iOS 系统要求的 1:1 / 3:4 比例或 macOS 的 1:1 比例内，原图保持比例、完整呈现并尽量铺满，只延伸无法覆盖的区域。不为所有封面额外增加一圈固定边框，不通过拉伸或裁掉主体减少留白。此处约束源视频的构图；全屏对源视频施加方形显示遮罩属于独立的展示操作。

原图与目标比例一致时不需要边缘延伸。比例不同时，只在缺少内容的方向居中补齐：上下或左右两边各承担一半。宽高比差异造成的必要延伸不能靠提高编码分辨率消除。

忽略编码对齐时，设原图为 `Ws × Hs`、系统目标为 `Wt × Ht`，且目标已经符合关联格式比例：

```text
r = min(1, max(Ws / Wt, Hs / Ht))
视频画布 = (Wt × r, Ht × r)
s = min(视频宽 / Ws, 视频高 / Hs)
原图主体 = (Ws × s, Hs × s)
左右各延伸 = (视频宽 - 主体宽) / 2
上下各延伸 = (视频高 - 主体高) / 2
```

这样画布不超过系统目标，原图主体也不会因适配画布而放大。编码时向下对齐尺寸并保持准确比例：1:1 可使用偶数边长；3:4 可使用 `6n × 8n`。对齐后重新计算主体与延伸区域，不得分别四舍五入导致比例错误。

| 平台与现状 | 处理结果 |
|---|---|

## 实现衔接

- 原图按目标需要解码，调整此前固定 1200px 的限制，避免先丢失细节后又放大；不要求始终把超大原图全尺寸解码到内存。
- 视频分辨率与 DAV2 FP16/P8/P6 档位分开管理。提高纹理输出尺寸不要求同步增大模型推理输入。
- 同一目标格式的 static、camera、depth 阶段使用相同的基础尺寸与构图，避免渐进替换时主体大小跳变。运动防露边余量单独核算并保持最小必要范围，不隐式增加固定边框。
- 系统尺寸需求晚于首次生成时，继续使用已有可用资产，后台生成更合适的版本后更新 artwork ID。视频 URL 回调仍仅读取成品，不同步推理或编码；不能只因为旧视频已缓存就永久停留在低分辨率。
- 实际输出宽高及算法版本进入缓存身份，避免新规则误用旧 720px 视频。静态原始视频保留、动态渐进发布、活跃租约保护和资源压力控制继续沿用既有约定。
- iOS 与 macOS 分别在各自平台目录中实现这些规则，通过消费契约和本文对齐行为；不增加跨平台源码引用。本次已分别修改两端原生实现与 Apple 平台的全屏消费路径；不新增 Web、Windows、Android 后端，也没有跨平台生产源码引用。


## 已实施的需求与展示分离

“生成需求”不是用户设置，不增加生成总开关。新增的用户开关是 **动态专辑封面**：位于全屏播放器的设置弹层和“设置 → 外观 → 全屏播放器”页面，默认关闭，持久化在 `settings.fullscreen.dynamicArtworkEnabled`。它只控制全屏消费者是否展示/使用视频，独立于 iOS 锁屏的两项展示开关。幅度、速度和模型设置可提前调整，不因锁屏展示关闭而禁用。

全屏启用且实际可见时先 acquire 成品，并单独登记带封面身份、模式、会话归属的消费需求。`acquire` 不启动生成。播放暂停或 Reduce Motion 时，消费者暂停现有视频，需求改为静态；离开可见封面、进入后台、关闭全屏或关闭展示选项时释放需求与租约。没有消费者时不因一个配置布尔值自动生成；iOS 锁屏发布器自身仍可按其展示需求工作，macOS 没有锁屏发布器，只有实际消费需求触发生产。

`format: "any"` 表示接受当前封面的任一可用比例与尺寸。原生优先返回最高完成阶段，同阶段取最新发布的成品；全屏使用居中方形 `object-cover` 遮罩，不将容器大小传给生成器。新视频读到首帧后再替换旧视频并释放旧租约。`motionAllowed` 单独表达原生资源/辅助功能许可，避免把后台升级期间的 static/pending 误认为必须停止已有动态视频，也避免资源受限时继续播放缓存动画。

## 原生分辨率落地

- iOS：`LockScreenArtworkRequests.swift` 按设备、OS、原生显示像素及格式保存 preview/video 两类记录。只有视频请求影响输出目标；预览不会冒充视频需求。无记录时，在原生屏幕像素边界内按格式向下对齐，明确标为 `provisional-native-screen (not a system request)`。收到新视频尺寸后异步通知生产者升级，现有文件与旧租约继续可读，不临时开启锁屏发布探测尺寸。
- iOS 与 macOS 各自的 `*Resolution` 使用本文公式、偶数/`6n×8n` 对齐及目标驱动 ImageIO 解码。macOS 无成品时以原图长边为方形目标，只补齐短边；有可用成品时先复用，即便它是旧分辨率或 3:4。生成器需要补建缺失的静态保留视频时，也不会重编码已有动态文件。
- 编码前按可用内存及物理 RAM 提供保守工作预算（约 80 bytes/pixel），超预算等比向下对齐；VideoToolbox 检查 H.264 硬件编码会话及 prepare，必要时继续缩小。iOS 17.4 以前使用旧版编码器探测路径。诊断记录 source/target/output/decoded pixels、目标来源及 `resource-budget` / `hardware-encoder` / 无法准备等原因，不将具体边长当作 Apple 统一规范。
- 同次生产的三个阶段共享尺寸与基础构图。运动位移按输出像素比例缩放，防露边只预留当前帧实际位移和插值需要的范围，不增加固定静态边框。同比例静态封面走无延伸快速路径。
- 新缓存身份为 static `edge-v2`、camera `motion-v7`、DAV2 `motion-v8`，均包含实际输出宽高；DAV2 继续包含幅度/速度。旧 v1/v5/v6 成品仅通过原图内容摘要、格式/参数校验后显式复用，不冒充新算法导出。原始静态视频、活跃租约保护、DAV2 后退休 camera 和资源控制继续有效。
